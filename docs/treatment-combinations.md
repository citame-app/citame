# Treatment combinations

Owners and managers use **Services → Treatment combinations** to prepare ordered selections of existing treatments, variants and compatible extras. These are booking shortcuts for one visit with one professional or sequential qualified professionals. The treatment and extra prices are added at their current catalog prices; no separate bundle discount or independent bundle entitlement is created. Use the promotion and package systems for those different commercial terms.

Choose at least two distinct items (up to 24), one option per treatment family, in the intended order. Extras follow an eligible treatment in the same currency. To move a treatment, remove it and select it again; check the displayed ordered list before saving. Every item must share a currency. Each treatment family and its extras must have a qualified active professional; the customer can choose one common professional or a complete sequential itinerary with several professionals. The normal booking rules continue to account for buffers, rooms, resources, dated hours, deposits and intake requirements. Processing gaps and parallel-client capacity follow their separately configured scheduling rules; see [processing and capacity](processing-and-capacity.md).

Customers can choose a combination on the first booking step, then adjust the individual selections. Choosing one replaces the previous selection. Its displayed price and treatment duration are calculated from the current client catalog; normal quote validation rejects changed prices/duration at confirmation. A common-professional appointment receives the ordered service IDs; a multi-professional visit receives the reviewed ordered parts through the transactional visit API. Each part keeps a separate receipt and subsequent cancellation/rescheduling lifecycle, as disclosed before confirmation. The API does not accept a client-supplied bundle price or waive any ordinary booking requirement.

New selections stop appearing when archived or when a required service/parent/professional is no longer available. The team list retains the record and identifies unavailable combinations. The operator can archive an unavailable combination without losing its original references. Changing its members or activating it again requires a valid current sequence. Archiving or editing a combination does not modify existing appointment service snapshots, dates, prices or payments.

Create requests carry a per-actor key and original content fingerprint. Concurrent identical retries recover one record. A later retry returns its current state, including an intervening edit/archive, without restoring old terms. Reusing a key with different content is rejected. Editing uses an optimistic version; stale edits preserve the visible draft and require closing, reloading and reviewing the current row. Unknown responses freeze the reviewed terms and retain the packet in memory for retry; discarding explains that the first request may already have committed and reloads the list. Drafts are not stored in browser storage. Catalog permission is checked again after acquiring the shared scheduling lock.

The salon limit is 100 records, including archived combinations; reuse an existing archived entry by editing it. There is no automatic merger of treatments, copied pricing or seeded public offer. This feature needs no external account.

Verification includes strict contracts, current qualification/currency/source rules, archive/version checks, concurrent create recovery, queued manager demotion, source withdrawal, web state preservation and actual ordered customer bookings. Browser runs cover light/dark mobile/desktop, long names, Spanish, lost create responses, stale edits, unchanged booked snapshots after archive, axe and horizontal overflow. Test data is synthetic.

For local production web verification, build `docker build -f docker/web.Dockerfile -t sob-web:citame-e2e .`, then run `bun run --cwd apps/web e2e:combinations:production`. This uses the same isolated local fixture and read-only runtime wrapper described in [booking entry](booking-entry.md); it does not deploy the site.
