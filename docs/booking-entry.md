# Booking links, QR and public widget

Owners/managers open Reputation → Booking entry. Choose public treatments (including their current variants/extras), optionally choose a professional who performs the whole selection, and copy the booking link or download its QR PNG. With no treatment selection the link opens the general booking page. Choose treatments before selecting a professional. Removed services/professionals block sharing until the choices are reviewed or explicitly cleared.

Links use the current browser deployment's origin; no domain is invented when none has been configured. Local test links therefore use localhost. Set the actual production HTTPS origin and verify links from that deployment before distributing them. Public links contain service/professional IDs, not a client's identity, appointment, private notes, slot, price, consent response or payment credential. Availability, prices and booking terms are reviewed again in the normal first-party booking flow. Copying/sharing a link does not create an appointment.

QR images are generated locally with pinned `qrcode` 1.5.4, a 512-pixel black-on-white PNG, four-module quiet zone and Q error correction. There is no remote QR/shortening/tracking service. Keep the white margin and original resolution; verify the final printed material on the intended physical surface before distribution. Native sharing is offered only where the browser provides it; clipboard failures preserve selectable text for manual copying. These controls do not publish anything to a social account.

The embed code contains a titled, lazily loaded `/widget` iframe with the same preselection. This page reads public catalog data only and never resolves/serializes an authenticated session, even when a cookie is present. It contains no account navigation or booking form. Its booking link opens the first-party site in another tab with `noopener noreferrer`, so sign-in, terms and payment run outside third-party cookie restrictions. The widget offers English/Spanish selection with the correct content language and keeps the normal catalog/error/empty states. Its preview can be opened in the admin page.

External embedding is **disabled until configured**. `BOOKING_WIDGET_ORIGINS` in the web container accepts up to 16 exact comma-separated HTTP(S) website origins, for example `https://www.example.com,https://example.com`. Include the scheme and port when applicable; do not use paths, query strings, credentials or wildcards. Invalid configuration fails startup. The empty default permits same-origin previews only. This setting is forwarded by `compose.prod.yaml`; reload/redeploy the web service after changing it.

Only a successful HTML response at exactly `/widget` gets the limited `frame-ancestors` exception. Other pages, server functions, error documents and API responses retain their original framing protections. The widget preserves the existing script/style nonce policy, form targets and other headers. Both `/book` and authenticated account/admin pages remain unframeable. No external website origin was supplied or enabled in production; loopback origins are used exclusively by the browser fixture.

The QR job is tied to the exact current link. A late result for an older selection cannot replace the current image, and failures retain the booking link and an explicit retry. Draft selections are not persisted in browser storage. Metadata-free portfolio images and website-only review permission do not automatically authorize reuse in social media creative; that remains a separate explicit permission workflow.

Verification includes executable tests for URL bounds/escaping, stale QR results, stale staff recovery, public-only session bootstrap, exact frame-policy scope and invalid configuration. Browser workflows decode the actual rendered/exported PNG with independent `jsQR`, check clipboard copies, open the booking popup, inspect private-session exclusion, render an approved cross-origin iframe, reject an unapproved iframe, switch to Spanish, and run axe/overflow checks on mobile/desktop light/dark. Production builds use pinned Bun 1.4.4 and frozen dependencies.

Primary implementation references: [node-qrcode](https://github.com/soldair/node-qrcode), [jsQR](https://github.com/cozmo/jsQR). Social account activation/publishing and real production-domain configuration are separate from preparing these local entry points.

To repeat the production web runtime checks on this Linux/Docker test setup, build `docker build -f docker/web.Dockerfile -t sob-web:citame-e2e .`, then run `bun run --cwd apps/web e2e:acquisition:production`. The fixture requires local Postgres/Valkey and reserves loopback ports 4273–4275 plus API port 4300. It uses an isolated fixture database and synthetic accounts. Playwright starts the web image with a read-only filesystem, bounded `/tmp`, pinned Bun 1.4.4 and no image pull. The named `sob-citame-web-e2e` container is disposable; it is not a production deployment.

The image's liveness probe follows `HOST`/`PORT`, including custom ports and IPv6 listeners. Production browser tests assert Docker's actual healthy state as well as page behavior. A test-only runtime wrapper handles SIGTERM/SIGINT, verifies its unique container ownership label, and explicitly stops that fixture through Docker; terminating only Docker's foreground CLI would otherwise leave the container running. It never stops a container belonging to another invocation.
